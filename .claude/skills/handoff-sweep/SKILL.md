# 清理 HANDOFF 待办

`HANDOFF.md` 是本仓库的交接台账（README「开发流程」：开始时读，结束时更新）。本 skill 把台账和实际状态对齐，然后只做已经有决定的事。

## 第 1 步：列出未完成的条目

1. 读 `HANDOFF.md` 全文和 README「开发流程」。
2. 列出所有没有标 `[已完成 …]`、`[已处理 …]` 或 `[已解决 …]` 的条目，包括各节的「待办」「待补」「未做」，以及「给方法库」里的 `[未处理]`。
3. 每条按下面四种分好，列给用户之前先自己核实，不凭条目原来的说法：

| 类 | 判断依据 | 处理 |
| --- | --- | --- |
| 已经做完 | 有提交号、文件或线上页面能证明 | 标为完成，写上核对依据 |
| 可以直接做 | 用户已经决定，或者不需要决定、在本仓库授权范围内 | 本次做 |
| 等用户决定 | 要选来源、要注册账号、有取舍、要付费 | 列给用户，写明选项，不替用户选 |
| 等别的仓库或日期 | 要方法库或 company-dossiers 的会话来做，或者约好了回看日期 | 不动；到期的提醒用户 |

## 第 2 步：核实

- **代码和文件**：`git log --oneline -- <路径>`、`git log --grep`、`grep -rn` 看条目说的东西在不在 main 上。
- **线上**：用内置浏览器打开对应页面，看网站最近几次 main 的运行（`gh run list --workflow pages.yml --branch main -L 3`）。
- **「给方法库」的 `[未处理]`**：只读方法库，看有没有处理（`git -C ../research-method-extraction log --oneline -20`，再 grep 它的缺口台账和 executions 里对应的记录路径）。处理了就改成 `[已处理 日期]`，后面加「处理结果：方法库提交 <号> …」；没处理就保持原样，不在本仓库替它写。
- **纠正候选**：位置记在本机的项目记忆里，不写进本仓库。只执行 `裁定:` 行已由用户标明采纳的条目，按「落点」去改；`裁定:  [ ]` 的条目不碰。
- **回看日期**：条目里写了「YYYY-MM-DD 前后回看」的，今天已到或已过就提醒用户。回看结果要另写记录，不改原登记。

## 第 3 步：做可以直接做的

- 每件事按它本身的规矩来：
  - 走查记录的改动用 method-replay 的规则，入库后不改写，只追加一节。
  - 发布用 publish-handoff。
  - 公共契约或研究计算的改动走 PR。
- 要动别的仓库的，交给那个仓库的会话：先看有没有正在跑的，有就用 SendMessage 发给它，没有就请用户开一个。本会话不直接改别的仓库。
- 做的过程中遇到要用户决定的事，停下来改成「等用户决定」，不自己选。
- 公开边界：本仓库公开，条目里不写个股判断、持仓、方法卡正文、邮箱、本机路径或 key。只能留在本机或私有仓库的结果，条目里只写「只在本机」和去向，不写数字。

## 第 4 步：更新台账并提交

1. 修改条目时保留原结论，方便以后核对：在行首加 `[已完成 YYYY-MM-DD]`，或在条目后补一句核对依据（提交号、页面、Actions 运行），不删原文。只有内容错了才改正，并写明为什么改。
2. 更新文件顶部的「更新于」日期。
3. 提交信息概括这次清掉了什么，例如 `Pending-work sweep: …` 或 `HANDOFF: mark … handled`。按 README「开发流程」走普通改动：建分支、`merge --no-ff`、跑 `uv run pytest`、推送 `main`。
4. 回复用户时分三块：
   - 这次做完的，每项写上依据。
   - 等你决定的，每项写上选项。
   - 等别的仓库或日期的。
