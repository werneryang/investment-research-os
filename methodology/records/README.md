# 提取记录

记录分两类，用 `record_type` 区分：

| 类型 | 含义 | 必填重点 |
| --- | --- | --- |
| `extraction` | 从一份材料提取作者的论证 | 研究问题、核心假设、证据、因果机制、判断错误的条件 |
| `application` | 把已有方法用到一家公司 | 方法输出 `method_output`，没有作者论点时 `thesis` 留空 |

从 [_template.yaml](_template.yaml) 复制，文件名用 `<来源>-<标的>-<日期>.yaml`。

提取记录的目的不是摘要，而是把论证拆开：作者研究什么问题，用什么证据，怎样推到财务结果和估值，什么情况下判断会错。

## 分层

每条内容必须标明层级：

| 层级 | 含义 | 必须有原文位置 | 可以标 `verified: true` |
| --- | --- | --- | --- |
| `source_fact` | 材料中陈述的事实 | 是 | 是，回原文核对后 |
| `author_judgment` | 作者的判断或推理 | 是 | 是，只表示作者确实这样说 |
| `ai_inference` | AI 重组或推导的内容 | 否 | 否 |
| `own_extension` | 自己提出的延伸问题 | 否 | 否 |

`verified: true` 只表示“与原文一致”，不表示内容正确。

计算结果放在 `method_output`：披露值、推算值、估算值分开，估算值标 `estimate: true`。

提取记录的 `evidence` 条目要写 `verifiability`，说明这条证据外部能否验证：

| 取值 | 含义 |
| --- | --- |
| `public_filing` | 可以用公开申报或官方数据核对 |
| `third_party` | 来自第三方研究、访谈或付费数据，公开申报核对不了 |
| `unverifiable` | 无法验证，或来源未说明 |

## 和方法库对照

`links.methods` 写明记录与方法的关系：

| `fit` | 含义 | 后续动作 |
| --- | --- | --- |
| `match` | 和已有方法一样 | 给方法增加一个案例 |
| `extends` | 基本相同，但多了步骤或适用范围 | 修改已有方法 |
| `conflicts` | 对同一问题给出相反做法 | 保留两边，写明各自成立的条件 |
| `new` | 库里没有 | 新建 `draft` 方法卡 |

## 修改规则

记录内容入库后不改写，发现错误时新增一条更正并说明原因。核对状态可以更新。

## 入库前检查

- 来源在 [sources.md](../sources.md) 中允许入库。
- 全部用自己的话写，不贴大段原文，不抄研报里的数字；需要时只记位置。SEC 申报的公开数字可以入库，但要写明申报编号和位置。
- 正确性存疑的指控类内容，只写成“需要核实的问题”。
